# Windows local CI runner plan

## Objective

Compile and test the WinUI 3 client on a Windows machine controlled by the
project, without depending on GitHub-hosted Windows runner budget. Keep the
existing GitHub Actions workflow format and use a self-hosted Windows runner that
connects outbound to GitHub over HTTPS.

This plan addresses the current validation block recorded in
[`windows-client-plan.md`](windows-client-plan.md): Actions run `35901077769`
could not start because the hosted Actions budget was exhausted.

## Non-goals

- Do not change the Windows UI toolkit from WinUI 3 to Avalonia, Qt, web UI, or
  another framework merely to compile on Linux.
- Do not expose an inbound port from the local network to GitHub.
- Do not use a developer workstation, personal credentials, or a shared file
  server as the runner environment.
- Do not run builds for untrusted forks or automatically expose repository
  secrets to self-hosted jobs.
- Do not implement an installer, signing, or release upload in this work.

## Chosen approach

Use one dedicated Windows 11 Pro/Enterprise or Windows Server VM as a GitHub
Actions self-hosted runner. The runner runs as a Windows service under a dedicated
non-administrator account and has a unique `review-radar-windows` label.

The runner polls GitHub over outbound HTTPS. It needs no public address, NAT
rule, VPN exposure, or inbound firewall exception.

## Phase 0 — Operator decisions and prerequisites

The operator, not an automation agent, must provide:

1. A dedicated, patchable Windows VM or server with a supported x64 CPU,
   sufficient disk for .NET/NuGet/Rust builds, and outbound HTTPS access to
   GitHub and NuGet.
2. A local administrator only for setup, plus a separate standard Windows user
   for the runner service.
3. The repository administrator access needed to add a self-hosted runner.
4. A choice of trusted execution policy:
   - **Recommended:** only `push` to `main` and manually dispatched workflows.
   - **Optional later:** trusted internal branches after an explicit review of
     who can push them.

Acceptance:

- The VM contains no personal SSH keys, GitHub CLI tokens, browser profiles,
  customer data, or mounted network shares.
- A VM snapshot or reproducible provisioning procedure exists before runner
  registration.

## Phase 1 — Provision the Windows build environment

Install and verify these components on the VM:

```powershell
winget install Microsoft.DotNet.SDK.8
dotnet --info
```

For the current WinUI foundation, `dotnet restore` must be able to retrieve the
Windows App SDK NuGet package. Before adding helper bundling or Windows release
packaging, also install Visual Studio Build Tools with the MSVC C++ workload and
the Rust `stable-x86_64-pc-windows-msvc` toolchain.

Create a runner work directory outside user profile/document locations, for
example `C:\actions-runner`, owned by the dedicated runner user. Ensure it has
no credentials or application capture/state databases.

Acceptance:

- `dotnet --info` reports a .NET 8 SDK.
- The runner user can create and remove files below the work directory.
- The build host can reach `github.com`, `api.github.com`, and NuGet over HTTPS.

## Phase 2 — Register and run the self-hosted runner

In the GitHub repository UI, open **Settings → Actions → Runners → New
self-hosted runner → Windows x64**. Download the runner archive and use the
short-lived registration command generated by GitHub. Configure a specific name
and label, for example:

```powershell
.\config.cmd --unattended `
  --url https://github.com/lukelex/review-radar `
  --token <registration-token-from-GitHub> `
  --name review-radar-windows-01 `
  --labels review-radar-windows `
  --work _work
.\svc install
.\svc start
```

Never put the registration token in source control, a workflow file, command
history shared with others, or LLM prompts. Confirm in the repository runner UI
that the runner is **Idle** and has the expected labels.

Acceptance:

- The runner appears online as `self-hosted`, `windows`, `x64`, and
  `review-radar-windows`.
- It restarts after a Windows reboot as a service.
- No public network listener was added for this setup.

## Phase 3 — Restrict the Windows workflow to trusted execution

Update `.github/workflows/windows.yml` in a separate commit:

1. Change the build job to:

   ```yaml
   runs-on: [self-hosted, windows, x64, review-radar-windows]
   ```

2. Remove the `pull_request` trigger while this runner is used. Keep `push` for
   `main` and `workflow_dispatch`.
3. Retain `permissions: contents: read` and do not add repository secrets to the
   build job.
4. Keep the job limited to restore/build until a Windows test suite exists.

Do not use `pull_request_target` as a shortcut: it can combine elevated context
with untrusted PR code. If PR validation becomes necessary, use a disposable VM
or restore a clean snapshot after every untrusted build.

Acceptance:

- A fork pull request cannot schedule code on the local runner.
- The workflow has no write permissions and no injected secrets.
- A push to `main` schedules the local runner by its explicit label.

## Phase 4 — Compile, diagnose, and harden the foundation

Dispatch the Windows workflow against `main`. The required build commands are:

```powershell
dotnet restore apps/windows/ReviewRadar.Windows.csproj
dotnet build apps/windows/ReviewRadar.Windows.csproj --configuration Release --no-restore
```

Fix all compile, XAML, package restore, analyzer, and warning-as-error issues in
small commits. Do not replace WinUI 3, change the shared Rust contracts, or add
Windows-only ranking/classification logic to make a build pass.

Then run the app interactively on the Windows VM with fixture/helper overrides.
Verify that it opens, presents the Tailored projection, keeps cached cards during
a refresh failure, and writes only under `%APPDATA%\review-radar`.

Acceptance:

- The GitHub workflow finishes successfully on the self-hosted runner.
- The local build has no compiler warnings introduced by the Windows project.
- The foundation behaviors listed in `docs/windows-client-plan.md` are observed
  on Windows, not inferred from Linux.

## Phase 5 — Ongoing maintenance

- Apply Windows, .NET, Windows App SDK, runner, and NuGet-cache updates on a
  maintained cadence.
- Periodically inspect runner service logs and remove stale build workspaces.
- Rotate/re-register the runner when the VM is restored or ownership changes.
- Keep Windows workflow permissions read-only until a separately reviewed release
  workflow needs narrowly scoped write permissions.
- Add fixture-driven C# tests and run them in the same workflow as the WinUI
  client grows.

## Deliverables

1. A documented, dedicated Windows self-hosted runner that is online and labeled.
2. A separate workflow commit that targets only that trusted runner and excludes
   pull-request execution.
3. A successful Windows CI run linked from `docs/windows-client-plan.md`.
4. Any source fixes needed for the WinUI build, committed separately from runner
   policy changes.

## Handoff instructions for an implementation LLM

1. Read `AGENTS.md`, `docs/native-client-contract.md`,
   `docs/windows-client-plan.md`, and this document first.
2. Do not register, reconfigure, or remove a self-hosted runner; that requires an
   operator-generated registration token and local machine access.
3. Before editing the workflow, confirm the runner label supplied by the operator.
4. Keep Windows workflow execution restricted to trusted `main` pushes and manual
   dispatches unless the operator explicitly approves a disposable untrusted-build
   environment.
5. Make the workflow-policy change, Windows source fixes, and documentation status
   updates in separate commits.
6. Validate Rust/Linux checks as required by `AGENTS.md`, then rely on the
   self-hosted Windows runner for `dotnet`/WinUI validation. Record any runner or
   budget block explicitly; do not claim Windows compilation passed without its
   output.
